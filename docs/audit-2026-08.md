## 👨‍⚕️ BAGIAN 1 — ROLE DOKTER

### 🟠 H1 — `selesaikanKunjungan`: tanpa transaksi + error tidak diperiksa
**File:** `app/actions/dokter.ts:559-709`

Fungsi ini melakukan **6 langkah tulis** berturut-turut: simpan rekam medis → hapus+insert resep → insert pembayaran → kurangi stok → update status → update attendance. **Tidak ada** DB transaction, dan **tidak satu pun** hasil `error` dari kelima langkah terakhir diperiksa (Supabase client tidak melempar exception — ia mengembalikan `{ error }`).

**Skenario kegagalan:**
- Insert `pembayaran` gagal (mis. constraint `pembayaran.kunjungan_id UNIQUE` — `schema.sql:139` — saat retry, atau RLS). Error diabaikan → eksekusi lanjut → **stok tetap dikurangi**, status tetap jadi `selesai`, fungsi return `{ success: true }`. Hasil: kunjungan selesai **tanpa pembayaran tercatat** (pendapatan hilang diam-diam).
- Bila salah satu langkah melempar setelah langkah awal commit → tidak ada rollback: resep sudah dihapus/ditulis ulang, stok sudah berkurang, tetapi status bisa tetap `diperiksa`. Retry gagal di insert pembayaran (UNIQUE) → kunjungan **macet permanen** dalam keadaan tak konsisten.

**Rekomendasi:** Bungkus seluruh operasi dalam satu **Postgres RPC/function** (transaksional) atau `supabase.rpc('selesaikan_kunjungan', …)`. Minimal: **cek `error` di setiap langkah** dan hentikan + laporkan bila gagal.

### 🟠 H2 — Pengurangan stok obat non-atomic (race condition / oversell)
**File:** `app/actions/dokter.ts:561-579` (pre-check) & `636-653` (decrement)

Pola *read-modify-write* klasik: `SELECT stok` lalu tulis `stok - jumlah` di statement terpisah, tanpa row lock / atomic decrement / transaksi.

**Skenario:** `stok=5`. Dua dokter menyelesaikan visit obat sama bersamaan (masing-masing minta 4). Keduanya baca 5, keduanya tulis 1 → **8 unit terdispensasi, stok tercatat 1** (hanya 4 terpotong). Diperparah `Math.max(0, …)` (`:647`) yang meng-clamp negatif → oversell tersembunyi total. Pre-check (`:561`) tidak menolong: TOCTOU, dan bila `obatData` null (RLS) guard `if (obatData)` (`:569`) **melewati** pengecekan sepenuhnya.

**Rekomendasi:** Atomic decrement lewat RPC: `UPDATE obat SET stok = stok - $1 WHERE id = $2 AND stok >= $1 RETURNING stok`. Jika 0 baris → stok tak cukup, batalkan.

---

### 🟠 H3 — Double-completion / double-charge tidak atomic
**File:** `app/actions/dokter.ts:555-557`

Cek `status === 'selesai'` lalu update status **tidak atomic**. Dua klik cepat / dua tab / retry realtime bisa lolos cek bersamaan → stok dikurangi 2×, attendance +2. Insert pembayaran ke-2 gagal (UNIQUE) tapi errornya tidak dicek (lihat H1). Tombol `saving` (`TabPembayaran.tsx:85`) hanya mencegah dalam satu tab.

**Rekomendasi:** Jadikan bagian dari transaksi H1; guard `UPDATE kunjungan SET status='selesai' WHERE id=$1 AND status<>'selesai'` sebagai kunci idempoten.

## 🖊️ BAGIAN 2 — CANVAS (HandwritingCanvas) & BEST PRACTICE

**File:** `components/dokter/HandwritingCanvas.tsx` (ada perubahan belum di-commit yang relevan).

### 🟠 H6 — `toDataURL('image/png')` dipanggil pada **setiap** gerakan pointer
**File:** `HandwritingCanvas.tsx:240-301`

`exportDataUrl` (useCallback) punya dependency `currentStroke` (`:295`). Effect `useEffect(() => { if (loadedInitial) exportDataUrl() }, [strokes, exportDataUrl, loadedInitial])` (`:297-301`) ikut `exportDataUrl`. Karena `currentStroke` berubah **tiap `pointermove`** (menambah 1 titik), identitas `exportDataUrl` berubah tiap gerakan → **`toDataURL` (encode PNG sinkron) dieksekusi tiap gerakan pointer** saat menulis. Ini penyebab utama lag ("nge-load terus"). Perubahan yang belum di-commit-lah yang menambahkan `currentStroke` ke sini.

**Selain itu:**
- `renderCanvas` (`:127-208`) mengalokasikan **offscreen canvas baru** (`document.createElement('canvas')`) setiap render — dan render terjadi tiap gerakan → tekanan GC tinggi.
- Kompleksitas O(n·m): setiap titik menggambar ulang **seluruh** stroke sebelumnya.

**Rekomendasi (perbaikan minimal):**
1. Export hanya saat `pointerup` (di effect `[strokes]`), **jangan** sertakan `currentStroke` di dependency export.
2. Reuse satu offscreen canvas via `useRef`, jangan alokasi tiap frame.
3. Bungkus render dalam `requestAnimationFrame` (throttle 1 frame/tick).

### 🟡 C-1 — Tidak ada handler `pointercancel`
**File:** `HandwritingCanvas.tsx:448-455` — bila sistem membatalkan pointer (palm, gesture OS), `isDrawing` tersangkut `true`, stroke aktif tak selesai. **Rekomendasi:** `onPointerCancel={handlePointerUp}`.

### 🟡 C-2 — Draft localStorage tak pernah dibersihkan
**File:** `HandwritingCanvas.tsx:120-124` menulis `hw_draft_${storageKey}` tapi tak pernah dihapus setelah simpan/selesai → akumulasi data stroke di localStorage seiring waktu. **Rekomendasi:** `removeItem` setelah `selesaikanKunjungan` sukses (mirip `sessionStorage.removeItem` di `TabPembayaran.tsx:133`).

### 🟡 C-3 — Titik stylus hilang saat menulis cepat (Apple Pencil/iPad)
**File:** `HandwritingCanvas.tsx:338-344` — hanya `e.clientX/Y` dipakai. Tidak memakai `e.nativeEvent.getCoalescedEvents()` → titik antar-frame terbuang, garis patah-patah pada sampling tinggi. **Rekomendasi:** kumpulkan coalesced events per move.

### ⚪ C-4 — Sumber kebenaran adalah PNG raster, bukan vektor
Vektor stroke hanya di localStorage (ephemeral); DB hanya menyimpan PNG hasil flatten. Edit ulang note lama = eraser menghapus piksel gambar yang sudah "dibakar", bukan stroke. Setiap edit membakar ulang PNG lama + stroke baru (degradasi generasi). **Rekomendasi:** simpan JSON vektor stroke di DB sebagai source-of-truth; render PNG hanya untuk tampilan.

### ⚪ C-5 — Palm rejection latch satu arah
**File:** `HandwritingCanvas.tsx:79, 322-327` — `isPenDetected` sekali `true` tak pernah reset; touch diabaikan selamanya untuk instance itu (dapat diterima karena remount per halaman).

### 🎯 Opsi Strategi Canvas (pilih salah satu)

**Opsi A — Perbaiki implementasi custom saat ini (effort rendah, risiko rendah).**
Terapkan H6 + C-1..C-3 di atas. Tetap `perfect-freehand`. Cocok bila ingin kontrol penuh & minim dependency. **Rekomendasi utama untuk jangka pendek.**

**Opsi B — Two-layer canvas + vektor di DB (effort sedang).**
Layer statis (stroke ter-commit) + layer live (stroke berjalan). Simpan JSON vektor di kolom baru (mis. `*_handwriting_strokes JSONB`), PNG hanya untuk preview cepat. Mengaktifkan edit non-destruktif & undo lintas sesi.

**Opsi C — Adopsi library matang (effort sedang, hemat maintenance).**
- `signature_pad` — ringan, khusus goresan pena, ekspor PNG/SVG bawaan.
- `react-sketch-canvas` — undo/redo/eraser/export siap pakai, berbasis SVG (skalabel, hemat ukuran vs PNG).
- `tldraw` / `excalidraw` — kaya fitur (berlebihan untuk sekadar coretan RME).
Trade-off: menambah dependency & kehilangan sebagian kontrol styling "kertas ivory".

## 🔐 BAGIAN 3 — KEAMANAN & RLS

> RLS **aktif di 9 tabel** (`schema.sql:188-196`), `.env` **tidak** ke-commit (baik). Ownership check alur dokter benar. Namun:

### 🔴 C1 — `resolveBreadcrumbLabel`: disclosure nama pasien via service-role tanpa auth
**File:** `app/actions/auth.ts:105-147`

Server action ini **tanpa `auth.getUser()` dan tanpa cek role**, namun memakai `createServiceRoleClient()` (`:109`) yang **bypass RLS**. Menerima `uuid` arbitrer dan mengembalikan **nama pasien** dari `kunjungan`/`pasien`. Bahkan pemanggil **tak terautentikasi** dapat menebak/enumerasi UUID dan mengambil nama pasien. **Rekomendasi:** wajibkan `auth.getUser()` dan gunakan client authenticated (hormati RLS), bukan service-role. Hapus juga `console.log` yang membocorkan nama pasien (`:124`).

### 🟠 H3 — Aksi keuangan tanpa cek admin (langsung dieksploitasi)
**File:** `app/actions/admin.ts:695-732` (`getKeuanganChart`), `734-770` (`getKeuanganDetail`)

Hanya cek `if (!user)`. Mengembalikan rekap pendapatan + nama/NRM pasien + resep. RLS `pembayaran` SELECT = `USING (true)` (`schema.sql:262-263`) → **RLS tidak memblokir** → **setiap user login (staf/dokter) bisa menarik seluruh data keuangan & PHI**. Fungsi keuangan lain sudah cek admin — dua ini gap yang tidak konsisten. **Rekomendasi:** tambah gate `role === 'admin'`.

### 🟠 H4 — `updateUser` / `toggleUserStatus` tanpa cek admin
**File:** `app/actions/admin.ts:78-101`, `103-123`

Hanya cek login. `updateUser` bisa mengubah `role`. Guard self-protect (`:84`) cacat: `staf` memanggil `updateUser(ownId, { role: 'admin' })` lolos guard. Saat ini **hanya** ditahan RLS `users` (admin-only). Satu regresi RLS = **privilege escalation penuh** / nonaktifkan akun rekan (DoS). **Rekomendasi:** cek admin di server action (defense-in-depth).

### 🟠 H5 — Gambar tulisan tangan medis di bucket publik (PHI)
**File:** `app/actions/dokter.ts:408-445` (`getPublicUrl` `:441`)

Penggunaan `getPublicUrl` = bucket `handwriting-notes` **publik**. Berkas berisi anamnesis/diagnosis/terapi tulisan tangan (PHI sensitif) dapat diakses **tanpa autentikasi** oleh siapa pun yang punya URL (URL tersimpan di DB, bisa bocor via log/referer/history). **Rekomendasi:** jadikan bucket **privat** + sajikan via **signed URL** berumur pendek. Hapus fallback service-role saat upload (`:419-433`).

### 🟡 M-SEC1 — Policy SELECT `USING (true)` terlalu longgar (over-expose PHI)
**File:** `schema.sql` — `pasien` (212), `kunjungan` (221), `rekam_medis` (235), `resep_obat` (253), `pembayaran` (262) semuanya `FOR SELECT ... USING (true)`. Setiap user login (termasuk staf front-desk) bisa membaca **seluruh** rekam medis, resep, dan pembayaran pasien mana pun. Inilah yang membuat H3/H4 dapat dieksploitasi. **Rekomendasi:** persempit ke prinsip least-privilege sesuai kebutuhan peran.

### 🟡 M-SEC2 — Banyak mutasi obat/pasien tanpa cek role
**File:** `admin.ts` `createObat`(163), `updateObat`(190), `addObatStock`(210), `toggleObatStatus`(242), `updatePasien`(298), `importPasien`(318) — hanya cek login; hanya ditahan RLS. Konsisten dengan pola H4.

### 🟡 M-SEC3 — Tidak ada validasi Zod di server
**File:** `lib/validations.ts` hanya dipakai di client. Server action (`createPasien`, `createKunjungan`, `createObat`, `saveRekamMedis`, `importPasien`) meng-insert `input` langsung tanpa validasi → panggilan langsung bisa menyimpan data sampah (stok negatif, `jenis_kelamin` invalid, field wajib kosong). **Rekomendasi:** validasi ulang di server.

### ⚪ L-SEC1 — LIKE wildcard tidak di-escape + `.or()` string mentah
**File:** `staf.ts:41,43,428,430`; `admin.ts:502,504`; `dokter.ts:464`. Saat ini di-gate regex `^\d+$`, jadi belum eksploitable, tapi rapuh. `%`/`_` user tidak di-escape. **Rekomendasi:** escape input sebelum interpolasi.

### ⚪ L-SEC2 — URL + anon JWT hardcoded sebagai fallback
**File:** `lib/supabase/client.ts:12-16`, `lib/supabase/server.ts:13-16`. Anon key memang publik (dampak rendah) tapi higiene buruk & menyulitkan rotasi. *(Service-role key TIDAK hardcoded — baik.)*

### ⚪ L-SEC3 — Middleware bypass saat header prefetch
**File:** `middleware.ts:60-63` — request dengan header `purpose: prefetch` / `x-middleware-prefetch: 1` melewati cek role/route. Ditutup oleh revalidasi di `layout.tsx:48-70` (baik), jadi tidak bocor. Tetap catatan: jangan jadikan middleware satu-satunya gate.

## 🏥 BAGIAN 4 — ROLE STAF & ADMIN (RINGKAS)

- 🟡 **NRM collision** — `staf.ts:56-72` `getNextNRM` pakai `max(nrm)+1`; dua staf bersamaan dapat NRM sama. Ditahan UNIQUE (`schema.sql:50`) tapi registrasi ke-2 gagal & harus diulang. **Rekomendasi:** DB sequence/RPC.
- 🟠 **Stok tak dikembalikan saat hapus pasien** — UI (`admin/pasien/page.tsx:959-976`) menjanjikan "stok dikembalikan" & `getPatientDeletePreview` menghitung `will_restore_stock`, tapi `deletePasien` (`admin.ts:559-583`) hanya CASCADE delete — **stok tak pernah dikembalikan**. Janji UI vs perilaku tidak sinkron.
- 🟡 **Timezone WIB vs UTC di laporan keuangan** — `getKeuanganSummary/Detail/DailySummary/DailyDetail/RangeDetail` & `getKeuanganChart` (`admin.ts:673-856`) membangun batas tanggal tanpa timezone terhadap `created_at` (UTC). Transaksi 00:00–07:00 WIB masuk hari/bulan yang salah → **total pendapatan harian/bulanan keliru** di sekitar batas tengah malam.
- 🟡 **Bug tanggal kunjungan (perlu cek)** — `kunjungan.tanggal DEFAULT CURRENT_DATE` (UTC server) sedangkan antrian dokter difilter `tanggal == <tanggal Jakarta>` (`dokter.ts:84,101`). Pendaftaran dekat tengah malam WIB bisa tak muncul di antrian hari yang benar. Pastikan staf set `tanggal` eksplisit dgn zona Jakarta.
- 🟡 **Tanpa transaksi di `createUser`** — cleanup gagal (`admin.ts:62-67`) bisa tinggalkan auth user yatim.
- ⚪ **Pasien impor terhitung "baru"** — `getPendaftaranStats` (`staf.ts:320-334`) bandingkan `created_at` ke hari ini; impor tak set `created_at` → pasien lama terhitung baru.
- ⚪ **`as any` pervasif pada write** — melewati keamanan tipe kolom.
